# 平台输出与编辑复核

## 格式与能力

内容结构与平台样式分开处理。先决定标题、正文、并列项、真实引语、代码、图片的语义，再转换到目标支持的形式。公众号的卡片、配色、HTML不能直接当成知乎样式。

本项目当前发布链路：blocks 仅支持 paragraph / heading，text 为纯文本。
- 标题用 heading；一般段落用 paragraph。单独段落优先单独 block；长文补丁 schema 不允许新增 block 时，可在原段内部按语义插入空行，保留原段索引。
- 并列项可逐项用 paragraph 加 `• `；有序步骤用 `1. ` 等文字编号。它们只是纯文本标记，不声称是富文本列表。
- 可少量用「关键词」或独立短段强调；原文引语用中文引号并保留出处，不能把作者自己的判断排成他人引语。
- 不输出等待渲染的 Markdown `**`、`>`、HTML、表格语法或代码围栏。需要代码且当前链路无法保真时，说明能力缺口，不破坏代码或声称已正确发布。
- 已有配图的 before_block 若受拆段影响，应保持其与原叙述的关联并同步调整；仅调整文章却无法同步配图时，不声称图文检查完成。

在其他支持富文本的目标中，可将少量重点转换为真实加粗，将真实引语转换为引用块。启用前确认整条链路能保存、渲染与重载验证，而非只检查生成文本中含有标记。

## 修改记录

利用既有稿件版本与审稿输入保存原文。记录原段位置、拆合/标题/标记变化和理由；不要复制整个长文到修改记录中。涉及事实和文笔的改写与纯排版修改分别注明。用户只要求排版时，不借机改写故事结局或中心判断。

## 复核顺序

1. 内容完整性：事实、限定词、来源与图片说明是否保留；引用归属是否清楚；故事中说话人与动作归属是否改变。
2. 阅读节奏：密集长段是否确需保留；连续单句段是否过碎；特殊文本是否被误拆；列表是否真有并列或顺序关系。
3. 标记语义：小标题是否有内容；强调是否稀疏；分隔是否代表场景变化；没有把无证据内容包装成重点。
4. 实际呈现：有预览工具时用约375–430px宽度检查，关注字号、段距、横向溢出、图片与标题位置。不要把某固定字数说成固定屏幕行数。没有预览时记录“结构检查完成，视觉效果待验证”。

排版检查不单独触发外部发布；遵循本次任务的授权与现有发布流程。
